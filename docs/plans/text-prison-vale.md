## 2. 目标、范围与三件套的职责

| 组成 | 负责什么 | 不承担什么 |
|---|---|---|
| `text-prison` Skill | 理解任务、提出适用的优化选项、按用户选择改写、核对原意、解释诊断 | 自动补齐未经来源支持的事实；额外调用评委模型 |
| Vale CLI | 根据明确配置报告词语、术语、链接文字等可机械检查的问题 | 证明语义、科研结论、读者理解或操作一定正确 |
| 按需规则库 | 用短文档保存规则来源、适用条件、例外与内容保护原则；用 Vale 配置选择机器规则 | 全量复制上游标准；把全部品牌风格同时加载 |

产品保留自动发现和显式调用。普通聊天、纯代码修改、逐字转录和纯 JSON 等机器可读输出不进入文风优化。现有 `structured` 路径将在获批实施时退出 Skill 入口；不恢复 JSON Schema 后端。

不维护或执行 Agent 实战、模型评委、A/B 实验、自动触发实验、基准、测试套件、fixtures 或评审网页。本文要求的单次方案审阅是用户指定的文档操作，不能扩展成实战评测。五个子模块仅供只读查阅，不运行其测试。

## 3. Skill 的任务交互

### 3.1 先确定本次工作

读取用户给出的文档、必要上下文和相关项目约定，确定读者、用途、语言、可编辑范围、原文与来源。用途沿用 `explanation`、`procedure`、`reference`、`research`、`agent-spec`；产品帮助由相应用途加 Microsoft 规则处理，不新增第二个 Skill。

只在缺失信息会改变结果或授权时询问。可以从材料判断的普通细节自行处理。自动发现只决定是否提出帮助；审阅请求不自动授权改写，用户原本已明确的修改范围也不因菜单而扩大。

### 3.2 给出适合当前文档的选择

对尚未选定优化方式、且存在实质不同方案的请求，提供 2–3 个有实际差别的选项，推荐一个。每个选项用简短文字说明修改范围、所用规则、Vale 调用次数、结构调整程度、用户复核重点和预期改善。不要求用户先理解规则包或配置文件名。短文本每个选项一行即可，不强制表格。

以下是 README 场景的**假设交互示例**，实际菜单应随任务改变：

| 选项 | 修改与规则 | 执行负担 | 预期效果与复核 |
|---|---|---|---|
| 局部清晰化（推荐） | 保留章节、标题和技术内容，使用 Google 技术表达与对应语言规则 | 读取用途、语言和一份品牌摘要；若 Vale 就绪，检查改写初稿一次，修订后至多复查一次 | 澄清指代、术语和条件；用户重点复核原意和命令上下文 |
| 按读者任务重组 | 先核对前提，再整理安装、最小用例和故障入口；采用同一品牌规则 | 除局部表达外调整结构；Vale 次数不增加，人工需复核章节顺序和链接 | 便于定位操作；可能影响标题锚点，必须同步查引用 |
| 仅检查 | 报告具体问题、位置和建议，不修改原文 | 读取所需规则；Vale 就绪时运行一次，无修订复查 | 提供可处理的问题清单，不保证穷尽语义问题 |

用户已经选定方案、限制“只改术语”或要求直接执行时，简短说明采用的范围后继续，不重复等待选择。“把这段改通顺”这类动作和对象明确、无需结构取舍的请求视为选择局部清晰化；仅说“优化文档”且可能涉及重组时给出选项。选项尚待回复时，不开始依赖该选择的改写。无交互工具时使用简短文字选项，不因工具缺失擅自接受默认项；无人回复的运行环境停在选择处。

结构优化若影响标题锚点，先查引用。跨文件修改已经包含在用户授权范围时同步处理；否则列出受影响位置，保留原锚点或请求扩大范围，不把“修复引用”当成修改其他文件的自动授权。

### 3.3 执行和交付

按选择加载规则并写作；只读必要的原文与来源。改写后对照原文核对主体、对象、否定、条件、不确定性、数字、单位、因果、版本和引用对应。代码、命令、标识符、公式、原样引文默认保护，除非用户明确要求修改。

来源缺失时，指出具体缺口及其影响，不补造前提、失败策略或验收条件。科研不把 `may`、`might`、`could`、误差范围和适用条件当成冗余删除。

完成初稿后可运行一次 Vale，处理适用诊断并最多进行一次针对性修订、一次 Vale 复查；仅检查模式不修改文档。未解决的实质问题交付给用户，不循环追求零警告或总分。原意核对由当前写作 Agent 完成，不是人工验收或独立语义验证。

“适用诊断”必须同时落在用户所选的文件、章节和修改类型范围内，并符合选项承诺。检查整个文件不扩大修改范围：范围外问题只在确实重要时列出，不顺手修复。局部清晰化不按标题规则改标题；只改术语不处理其他表达提示。统一顺序为“按选择写出初稿 → Vale 检查 → 一次针对性修订 → 至多一次复查”；仅检查模式直接检查原文一次。

最终交付优先给文档或改动入口，并简要列出实质重排、待确认信息及 Vale 状态。不要给每次润色附加大篇审计报告；纯机器格式请求不混入诊断文字。

### 4.1 规则选择

| 任务 | 人工写作规则 | Vale 默认配置 |
|---|---|---|
| 英文 README、教程、API、技术解释 | Google + 用途 + 英文；操作章节可加 STE-inspired | `dev-en.ini`，操作文档用 `procedure-en.ini` |
| 英文 UI 文案、产品帮助 | Microsoft + 用途 + 英文 | `product-en.ini` |
| 英文科研说明 | 科研内容保护 + 英文清晰性；只按需要参考品牌原则 | `research-en.ini` |
| 英文 Agent 指令 | 目标、权限、条件、对象和停止条件 | `conservative.ini` |
| 中文文档 | 中文 + 用途；可借用品牌的组织原则 | `zh.ini` |
| 中英混合或多用途文档 | 按章节优化；保持项目既有约定 | `conservative.ini`，不全局套英文风格 |

每个文档默认只选择一个品牌主线。Google 和 Microsoft 的组织原则可以人工按任务借鉴，但不把两个 Vale 包全量叠加。STE-inspired 仅用于适合的操作消歧，不对科研或普通中文施加受控英语词典约束，不声称完整 ASD-STE100 合规。

按需读取上限采用内容范围而非未经测量的 Token 数：通常一份用途、一份语言、至多一份品牌摘要；只有操作说明确有需要时再读取 STE 摘要。核心保护原则留在 SKILL.md，避免每份参考重复。

规则分工参考 [Google Highlights](https://developers.google.com/style/highlights) 与 [Microsoft Top 10 tips](https://learn.microsoft.com/en-us/style-guide/top-10-tips-style-voice)。这些是写作建议来源，不证明本项目的收益幅度。

## 5. Vale 配置及诊断约定

### 5.1 规则与包

Vale 是唯一机械引擎。配置以相对 `StylesPath = styles` 引用随配置分发的原创规则，路径相对于设置它的配置文件。初版把 [Vale v3.25.1](https://github.com/vale-cli/vale/releases/tag/v3.25.1) 作为文档与配置基线，接受不低于 3.25.1 的 3.x 版本；这是一项维护范围选择，不是对更老版本不兼容的实测结论。较老版本、未知版本或新的大版本先记 `Not Run`，不擅自升级。[StylesPath 官方说明](https://docs.vale.sh/keys/stylespath)

英文开发配置声明固定的 [Google v0.7.1 规则包](https://github.com/vale-cli/Google/releases/tag/v0.7.1)，英文产品配置声明固定的 [Microsoft v0.15.1 规则包](https://github.com/vale-cli/Microsoft/releases/tag/v0.15.1)。这是本方案选择的基线，不宣称最新版本。

| 配置 | 上游包 | 首次使用是否同步 |
|---|---|---|
| `dev-en.ini` | Google v0.7.1 | 是，未在同一目录同步过时 |
| `procedure-en.ini` | Google v0.7.1 | 与开发配置共用已有的 Google 包，不重复同步 |
| `product-en.ini` | Microsoft v0.15.1 | 是，未在同一目录同步过时 |
| `research-en.ini` | 无 | 否 |
| `zh.ini` | 无 | 否 |
| `conservative.ini` | 无 | 否 |

六份配置均使用上述 CLI 基线，并显式设置 `MinAlertLevel = suggestion`。科研、中文和保守配置仅启用适用的原创规则；STE-inspired 是人工写作参考，不对应另一个下载包。[MinAlertLevel 官方说明](https://docs.vale.sh/keys/minalertlevel)

在相应 `Packages` 字段使用固定发布 ZIP URL：

```ini
Packages = https://github.com/vale-cli/Google/releases/download/v0.7.1/Google.zip
```

Microsoft 使用同样结构的固定地址 `https://github.com/vale-cli/Microsoft/releases/download/v0.15.1/Microsoft.zip`。不在 Skill 运行中下载，也不提交同步得到的第三方包副本。同步步骤只针对用户所选配置，不为中文用户下载两个英文包。

六份配置共用一个 `styles/`，因此需防止包附带配置造成串扰。已静态读取上述固定标签的 [Google 发布脚本](https://github.com/vale-cli/Google/blob/v0.7.1/.github/workflows/main.yml) 和 [Microsoft 发布脚本](https://github.com/vale-cli/Microsoft/blob/v0.15.1/.github/workflows/main.yml)：它们分别打包同名规则目录；已查阅的目录中没有包内 `.vale.ini`。这是源文件依据，未下载核验发布 ZIP。实施和后续更新须检查包布局；若包引入 `.vale.ini`、嵌套依赖或共享配置，先修订隔离方案，不能沿用当前假设。`vale sync` 会重建 `.vale-config/`，并可能覆盖同名包或资源，故用户定制不能放在上游包目录。[Packages 官方说明](https://docs.vale.sh/keys/packages)

初版采用保守的显式启用列表：`BasedOnStyles` 只包含项目自己的基础规则，按官方支持的 `Style.Rule` 设置启用选定上游规则，避免全量套用后再不断屏蔽。实施时从固定版本核对实际规则文件名、消息和适用语言，在 `vale/README.md` 记录启用列表和理由；不能猜测规则名。具体名单须在实施交付中可见。[Vale BasedOnStyles 与单项规则设置](https://docs.vale.sh/keys/basedonstyles)

初版原创规则限定为中英文缺乏意义的链接文字，例如“点击这里”和“click here”，只检查适用的链接文字作用域。中文 existence 规则按官方定义使用 `nonword: true` 去掉默认单词边界，不能照搬英文模式；规则名、模式及排除项必须列在 `vale/README.md`。中文机械覆盖很小，不宣称一般中文语法检查。项目术语优先读既有词汇配置或文档；若不存在机器词表，初版只由 Agent 核对，不自动生成、维护多份术语规则。[Vale existence 规则](https://docs.vale.sh/checks/existence)

中文不加载英文拼写、词数、语态、冠词或大小写规则。科研配置及保守配置不启用“禁用第一人称”“禁用被动语态”“禁用不确定性”或全局极短句要求。无法用少量稳定规则准确表达的建议放在人工参考中。

不同配置的保护要求相同：代码块、行内代码、公式、原样引用不因风格检查而改动。实施时按 Vale Markdown 作用域核对排除项，原样引文需明确配置；链接文字可检查，链接目标不改写。不能把“编辑时保护”误写成 Vale 对所有格式天然完全忽略。[Vale Markdown 格式与作用域](https://docs.vale.sh/formats/markdown)

### 5.2 明确输入、配置和结果

文件输入必须存在；初版支持 Markdown 和纯文本。粘贴片段及尚未落盘的新稿，可在宿主能够可靠传递 UTF-8 stdin 时直接输入 Vale，并显式指定 `--ext=.md` 或 `--ext=.txt`，不创建临时文件。无法可靠传递 stdin、无法确定应匹配的项目文件作用域时，记为 `Not Run` 并说明原因；不为检查擅自保存文档。[Vale 文件与 stdin 输入](https://docs.vale.sh/topics/cli)

DOCX、PDF、HTML、MDX 等没有已确认处理方式时，说明不支持，不自动安装转换器或把原件重写成临时格式。混合语言使用保守配置，不实现自动语义分段分类器。纯文本没有 Markdown 的代码、引文及链接作用域：只有可明确应用的纯文本规则才运行；没有适用规则时记 `Not Run`，不能把未覆盖的正文说成零问题。

Skill 先核对输入方式、实际安装位置、Vale 可执行程序和版本、配置及所选包是否就绪，再运行参数数组或正确引用的命令。文件输入禁止因路径拼错而让 CLI 将其当作直接文本检查。配置路径用实际绝对路径，目标文件逐个明确传入；不默认扫描整个仓库。

包就绪先看所选配置实际引用的目录和启用规则文件是否存在；仅目录存在不证明版本或完整性。记录并核对用户首次同步时的包版本信息，信息不足就说明版本未确认，不伪装成固定版本已核实。缺少必需文件在调用前记 `Not Run`；实际调用中发现配置损坏或资源加载错误则记 `Failed`，两者不互相掩盖。

示意命令如下，实际值由用户安装位置和目标文件决定：

```powershell
$skillRoot = 'D:/path/to/project/.agents/skills/text-prison'
$configPath = Join-Path $skillRoot 'vale/dev-en.ini'
$documentPath = 'D:/path/to/project/README.md'
vale --config $configPath --no-global --output=JSON $documentPath
```

`--no-global` 用于避免隐式混合全局配置；返回内容由当前 Agent 阅读，不建立自研检查结果服务。规则选择、显式配置和 CLI 参数以 [Vale CLI 文档](https://docs.vale.sh/topics/cli) 为依据。

若项目已有配置，先读相关设置，默认使用 `--config <项目配置绝对路径>` 运行，并保留原文件。示意命令中的 Skill 配置适用于没有项目配置或用户已选择它的情况。改用 Skill 配置的差别合并到同一轮优化选项，不另加一次重复选择。项目包缺失记 `Not Run`，不代为同步；与中文或科研保护冲突的提示不用于改写原意。

默认保留 `--no-global`；若项目明确依赖全局配置或资源，在选项中说明该依赖并确认采用范围，不隐式取消此参数。实际运行的配置、来源及覆盖范围需如实说明，项目规则不能被称为 TextPrison 的固定规则集；项目依赖或转换器也不得隐式安装。

运行后同时看退出码、stdout 与 stderr。按当前 CLI 文档，`0` 表示运行完成且没有 error 级提示，仍可能有 warning/suggestion；`1` 表示运行完成且有 error 级提示；`2` 表示工具、配置或文档处理出错。未知退出码、错误对象或不能解释的输出记 `Failed`，不只凭 JSON 可解析判断成功。正文诊断应是按输入标识组织的提示列表，并核对实际检查对象；没有适用规则或目标未覆盖需明确说明。默认不用 `--no-exit`。这些语义已核对官方文档，尚无本机运行证据。

| 状况 | 对用户的说明与处理 |
|---|---|
| Vale 不存在、版本不在范围内、所选规则缺失或无适用输入 | `Not Run`，指出具体原因；保留已完成的写作工作，必要时提供手动安装/同步步骤 |
| 配置无效、文件不可读或 CLI 失败 | `Failed`，报告具体错误，不改成“零问题” |
| 运行完成并有提示（退出码 0 或 1） | 说明检查完成、有诊断；逐项判断规则和授权范围，给出位置和建议；不把风格提示等同于工具运行失败 |
| 运行完成且没有适用诊断 | 只说明所选规则未发现问题，不宣称语义或理解效果通过 |
| 误报 | 保留原文含义，解释不采纳理由；不为一次误报关闭全局规则 |

局部忽略或词汇表变更会写入文档/配置，只有在用户授权该修改范围时采用，并注明理由。不能为了隐藏警告擅自改变检查范围。

## 6. 安装与日常使用文档

### 6.1 安装责任和主线

本方案只交付仓库文件和可执行的安装介绍。实际安装 Vale、同步上游包、修改其他项目或全局配置需要另行明确授权；Skill 不自动完成这些操作。

安装文档使用 Windows PowerShell 为主线，每步给出前提、工作目录、动作、成功标志及失败处理。macOS/Linux 仅拆分安装 Vale 和 shell 语法确有差异的部分。

1. 用现有 Python 运行项目安装器，把 `skills/text-prison/` 复制到明确存在的目标项目；安装器拒绝覆盖。
2. 通过 [Vale 官方安装说明](https://docs.vale.sh/topics/installation) 安装 CLI；Windows 提供官方包管理器和发布包两种路径，优先介绍 `winget install -e --id errata-ai.Vale`。安装器不会执行此命令。
3. 核对 `vale --version` 并对照随 Skill 分发的 CLI 基线；这只证明程序能启动并显示版本，不证明规则正确或集成有效。
4. 选择所需配置，按配置表决定是否显式运行 `vale sync --config $configPath --no-global` 下载固定包；同步前说明会写入所选 Skill 的 `vale/styles/` 并替换同名上游资源。无包配置不运行 sync，不在上游包目录保存定制。
5. 按文档给出的具体文件路径进行日常调用，理解诊断和未运行状态。此使用示例不在本仓库自动执行成测试。

### 6.2 更新、维护及冲突

安装器不覆盖已有 Skill、不安装 Python 包、不创建全局规则或 hooks。它目前生成逐文件 SHA-256 的 `install-manifest.json`；更新时据此区分分发文件的本地改动和后续同步包。获批实施时为复制过程精确排除 `vale/styles/Google/`、`Microsoft/`、`.vale-config/`，避免源目录中偶然同步的内容被打包。不能排除整个 `styles/`，否则会丢失原创规则。

随 Skill 携带的 `vale/styles/.gitignore` 只忽略上述生成目录，不修改目标项目根 `.gitignore`。安装说明明确此行为；需要提交上游包的用户自行决定调整。未知目录和本地定制不能被当成缓存删掉。

手动更新流程为：核对 manifest 和本地改动 → 列出原目录保留位置、替换范围并取得批准 → 将已确认的旧副本保留到用户选定位置 → 用现有安装器安装新副本 → 人工合并仍适用的配置和词汇定制 → 用户明确授权后按新配置同步固定包。保留旧副本直到用户确认新副本可用；不自动删除，也不新增更新程序。

固定上游版本更新属于依赖变更，需要说明变化和授权；没有“每次运行同步最新”的步骤。多宿主默认各自使用完整、自包含的配置与包目录：`both` 的两份副本若都用于英文检查，就分别同步；只用一个宿主则只维护该副本。初版不创建跨副本链接或共享运行路径。项目术语事实只维护在项目既有词汇配置或术语文档中；无此材料时标出缺口，不在每份 Skill 副本生成术语库。用户主动定制副本时需自行同步各副本，文档明确这一维护负担。

用户只使用文字指导时无需 Vale；需要机械检查时才承担 CLI 安装和首次包同步。运行负担通常是一次本地检查，修订后最多再检查一次；没有额外模型评委。加载规则和人工核对原意仍会占用时间，不承诺固定 Token 节省比例。

默认不安装 Vale Agent 插件、MCP、编辑 hooks、CI 或 zhlint。官方 [Vale agent-tools](https://github.com/vale-cli/agent-tools/blob/main/README.md) 可作为将来的集成参考，本轮不引入其多 Skill、hook 或额外依赖。
