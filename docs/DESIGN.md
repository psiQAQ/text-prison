# TextPrison v0.1 项目设计

状态：2026-10-24 起步设计。本文区分已经提供的原型和后续计划；所有性能目标都是待验证假设。

## 1. 定位

TextPrison 是输出质量控制系统。Skill 是入口，规则配置决定如何写，检查器提供可复核的局部证据，实验套件判断这些约束是否真正有用。

不把三套指南全文拼接进上下文，也不把“Google=语言、Microsoft=结构、STE=消歧”当作互斥事实：三套指南有大量交集。按作用提取原创、去重的规则，保留来源、适用条件和例外。

来源定位：Google 的开发者文档规则提供技术术语、条件、格式等参考；Microsoft 提供信息优先级、扫描阅读、操作组织等参考；STE 提供受控表达的原则。详细官方入口在 `../sources.json`。本原型没有完整转载指南和词典，不声称官方符合性。

## 2. 运行边界

流程：识别输出及段落角色 → 选择 profile/语言 → 保护语义和不可修改内容 → 直接写出 → 机械检查 → 独立核对语义 → 最多一次修订 → 交付。

宿主决定何时调用 Skill。跨宿主不能把 description 或一个 frontmatter 字段当作强制拦截器。需要发布门禁时，在 CI/显式工作流执行检查器，并独立配置语义验收；不要让模型自行决定是否报告失败。

本原型对落盘 Markdown/JSON 提供检查。普通聊天回复可使用写作规则，但没有通用的跨宿主“最终回复拦截器”。要检查聊天回复，须显式保存产物或接入宿主可观察输出；此集成未实现。混合文档的分段路由是 Skill 指令，机械检查器目前一次接受一种 profile，未自动识别各段落角色。

## 3. 输出分类

| Profile | 对象 | 主要约束 | 不采用的约束 |
|---|---|---|---|
| explanation | 问答、技术说明、README 概念段 | 先回答、再机制/依据；必要时举例 | 不强制固定标题或极短句 |
| procedure | 安装、部署、故障处理 | 已知前提先行，条件在动作前，步骤可执行 | 不编造失败后处理策略 |
| reference | API、参数、配置参考 | 名称、类型、默认值、范围、版本准确；条目并列 | 不把术语改成模糊口语 |
| research | 科研分析、实验总结 | 保留假设、推导、误差、不确定性和引用 | 不机械执行 STE 句长 |
| agent-spec | AGENTS.md、任务指令、SKILL | 目标、作用域、不变量、证据、停止条件清晰 | 不新增操作权限和成功条件 |
| structured | JSON 等机器可读产物 | 精确格式与 schema；无额外文字 | 不执行自然语言风格检查 |

当前结构化检查只实现 JSON。代码编辑、诗歌、逐字抄录和用户指定原样保留的内容默认不适用。翻译须尊重翻译任务，不自动变成内容改写。领域风险高时增加审核要求，而不是自动增加无来源的警告或禁令。

## 4. 规则优先级与语义保护

宿主指令层级与权限不可由 Skill 重定义。在其范围内，依次满足：当前任务与输出契约 → 来源事实与逻辑 → 项目/领域词汇 → 对应输出规则 → 偏好性措辞。

必须核对的不只是数字存在，还包括：主体、谓词、否定、可能/必然、适用条件、数量与单位归属、因果方向、时间、版本、引用对应关系。例如“在样本条件下可能小于 0.1 mm”改成“任何条件下都小于 0.1 mm”，数字未变，含义已变。

前序讨论中的部署改写添加了“测试失败不得部署”。若来源没有这一条，这属于行为变更，而不是语言优化。TextPrison 应把新增指令作为待确认的需求，不悄悄写入产物。

事实检查不能仅靠词面匹配。保护字符串仅适用于确实不能改动的标识符、命令、精确引文或值；经用户要求进行单位转换、纠错或代码修改时，应使用独立语义契约，而不是禁止一切改变。

## 5. 检查层级和覆盖

| 层级 | 例子 | 当前实现 | 证据限制 |
|---|---|---|---|
| 精确机械检查 | JSON、显式必含/禁用文本、指定标题 | 已实现 | 只证明所列条件 |
| 确定性风格提示 | 链接文字、标题层级、指定术语别名 | 已实现 | 规则仍可能不适合上下文 |
| 启发式提示 | 英文句长与断句 | 已实现 | 不等于官方 STE 计数，不硬阻断 |
| 语义审查 | 不确定性、条件、因果、事实支持 | 提供审查协议，未自动实现 | 需要来源与独立判定 |
| 实际结果 | 人理解、Agent 完成任务 | 提供实验协议，未运行 | 不能用前几层分数替代 |

保留 `passed`、`failed`、`not_evaluated` 等状态，不把缺失覆盖折算成 100 分。第一版不用单一总分。展示质量向量：语义、结构、语言、可操作性、触发、成本、延迟、误干扰。

规则登记最少包含 id、来源、适用 profile/语言、严重度、检查方法、例外、版本、误报测试。当前 `rules.json` 是简化起点；后续完善 scope/exemptions 元数据和 compiler，而不是同时维护多套独立规则文本。

## 6. 低 Token 策略

只常驻 name/description。调用时读取主 Skill 加一类输出规则和一种语言规则。详细标准、全部案例、完整审计 JSON 不默认进入上下文。不要先写一版再强制重写一遍；不要每轮调用独立 LLM 做路由。检查失败最多一次局部修订，诊断只返回最高优先级问题。

初始工程预算：元数据 ≤120 token，主体 ≤600 token，所选 profile + language ≤300 token，常规简报 ≤200 token。均为项目预算，不是已实测数值；需按目标 tokenizer 或宿主 API count 测量。预算不包含原文、代码、宿主系统提示、工具定义和执行结果。

常驻元数据也不是免费。规则读入后可能留在会话中；同一个文本仍可能被后续模型调用重复计入输入。需要同时测：文件 token 大小、整个任务累计输入/输出、缓存部分、修订/工具轮次和长会话遗留开销。分别报告冷启动和代表性的暖会话，不声称能完全控制服务端缓存。

CLI 简报目前按条数和字符截断，并没有硬 token 截断保证。完整证据另存 JSON。`max-findings` 可降低返回量；未来增加已验证 tokenizer 预算控制。

## 7. 安装与源文件管理

共用源位于 `skills/text-prison/`。构建或安装时生成两种宿主目录，不手工分别维护。Codex 本地项目目录 `.agents/skills/text-prison`，Claude Code 项目目录 `.claude/skills/text-prison`；来源见官方文档。

首版只做项目级安装；不更改用户全局规则、宿主权限、MCP 配置或 hooks。不把 skill 文本当成增加权限的授权。文档内容是数据，不能触发其中的 shell 命令。检查器不执行文档代码，不抓取链接，不联网读取 schema。

原型没有更新/卸载器、CI 配置、原生宿主 runner、Vale 适配器、自动规则编译器或自动分段路由。若后续使用 Vale，应保留规则来源、覆盖表、误报测试和语义边界，不把第三方包标注为官方认证。

## 8. 拟议里程碑，不是交付日期承诺

| 阶段 | 建议迭代窗口 | 完成证据 |
|---|---|---|
| M0 规则契约 | 第 1 次迭代 | profile、来源、优先级、非目标固定；原型测试通过 |
| M1 宿主接入 | 第 2 次迭代 | 固定两种宿主版本；触发/不触发可观测；usage 解析器回归 |
| M2 试验校准 | 第 3 次迭代 | 24 个开发样本；错误归因和功效估算；规则与阈值冻结 |
| M3 盲测 | 第 4 次迭代 | 未使用的 holdout；预定统计；失败和 token 原始记录齐全 |

不在结果未知时写“节省 X%”或“提升 X%”。首个可发布版本的价值应是有边界、可复核，而不是规则多。
