# 大模型输出可读性调研报告

日期：2026-10-26。对象：中英文技术文档、科研说明和面向人的技术回答。仓库基线：`c6073e9e9dd2`。

本文保留研究结论与工程建议的区别；本地 P0＋P1 的实际采纳范围及静态核对另见[实施记录](../../plans/2026-10-26-readability-evolution.md)。原基线审查不代表修改后的运行效果。

## 1. 结论与建议

**TextPrison最值得改善的不是“压得更短”，而是“让读者少猜一层”。** 建议把原意保护作为不可牺牲的约束，将动作、对象、条件和论证关系写清楚；机械规则只承担能明确检查的部分。这个方向是在现有仓库上增加小幅写作指导，不需要另一套后端。

本报告建议保留三种职责：当前Agent负责结合来源改写；Vale负责所选显式规则；AutoCorrect仅按需处理中文排版。该分工与[当前设计](https://github.com/psiQAQ/text-prison/blob/c6073e9e9dd2f66c6e823c9dfc9818ea641bd584/docs/DESIGN.md)一致。提示词候选见[04-prompts.md](04-prompts.md)，具体文件改动见[演进计划](../../plans/2026-10-26-readability-evolution.md)。

## 2. 对起点论文和传播说法的核查

[种子论文P00](https://arxiv.org/abs/2610.29162)于2026-10-21提交。它比较了9款前沿/近前沿及5款较小模型的英文输出，检查低频词组、依存距离、名词堆叠等特征；另用带长度惩罚的小模型微调展示一种可能机制。这里有语言特征的比较和机制示例，不是对所有商业模型训练过程的审计，也不是中文读者理解能力的直接实验。

因此，不能由此断言所有新模型都越来越难读，或所有强化学习都在奖励短回答。特别是[长度与RLHF研究P03](https://arxiv.org/abs/2310.03716)在所测设置中发现，奖励模型偏差会推动更长的输出。更合理的判断是：训练目标、数据偏好和任务环境都可能改变表达；具体模型需要具体证据。P00的往返翻译也是研究对照，不应直接当作可靠的生产改写器。

传播文字中的“单稿成本相差72倍”没有在本报告中作为已核实事实使用；它不能由P00推出。本轮不提供ToneBench排名或价格结论。名人使用某项写作规范的建议，也不等于该规范已经在你的中文科研文档中验证有效。

## 3. 先区分五个目标

下面是本报告用于工程选型的分类，不是论文统一采用的评分体系。

| 目标 | 读者实际需要什么 | 不能用什么替代 |
|---|---|---|
| 读得顺 | 不反复猜修饰关系和指代 | 仅统计句长、字数 |
| 看得懂 | 理解概念、条件和结论之间的关系 | “没有生僻词” |
| 找得到 | 快速定位所需答案、步骤或参数 | 把所有句子拆成项目符号 |
| 不失真 | 数值、否定、范围、证据强度保持一致 | 文风更自然、模型自评分高 |
| 用得上 | 能按已知前提完成目标任务 | 排版工整、工具零告警 |

[Google写作指导S01](https://developers.google.com/style/highlights)提供条件与动作、明确执行者、链接文字等建议；[Microsoft指导S02](https://learn.microsoft.com/en-us/style-guide/scannable-content/)强调重要内容前置、结构和导航。它们是写作指导，不是你的项目已有读者收益的实证证明。

## 4. 难读问题与可采用措施

以下“措施”和“例外”是本报告的工程建议；研究依据分别在[文献地图](02-literature.md)中说明。

| 问题 | 读者卡在哪里 | 优先措施 | 必须保留的例外 |
|---|---|---|---|
| 多层名词连用 | 不知道谁修饰谁、用途还是对象 | 将确有歧义的部分展开成“用于…的…”或完整动作句 | 固定术语、产品名、标识符不拆 |
| 省略逻辑关系 | 不知道是条件、原因、对比还是并列 | 在来源支持时明确连接关系 | 没有依据时不得补“因此” |
| 主体或指代不明 | 不知道“它”是哪一个对象 | 重复必要名词，写明已有执行者 | 执行者未知时不强造主动句 |
| 修饰语插入过多 | 读到结尾才找到主句动作 | 把非必要插入信息移到邻句 | 条件和否定的作用范围不能变 |
| 陌生拟人化和隐喻 | 必须先解码比喻再读事实 | 技术说明优先直接描述机制 | “服务器返回响应”等正常搭配保留 |
| 过度碎片化 | 每段很短却不知道如何连接 | 恢复完整句和段间联系 | 表格字段、步骤标题无需补成散文 |
| 抽象套话 | 看不到实际对象和动作 | 用可验证的具体描述代替 | 原文没给细节时标缺口，不补造 |
| 信息组织失配 | 明明都写了，却找不到答案 | 答案前置；按读者任务组织 | 科研推导所需次序不能随意颠倒 |
| 中文混排混乱 | 阅读时受空格、标点打断 | 沿用项目排版；可选AutoCorrect | 单位、公式、引文、UI原文保护 |
| 简化导致失真 | 读起来轻松但理解错了 | 对照来源逐项检查改动 | 不以“更通顺”为由删除保留项 |

优先级应是：先修会改变理解的歧义，再处理任务结构，最后处理低风险排版。对一个已经清楚的段落，不应为了规则命中而强制改写。

## 5. 哪些研究支持这些取舍

[法律文本研究P06](https://mollicaf.github.io/publication/martinez-202-xwhat/)通过语料分析和读者实验区分复杂句法与专业概念的作用。它支持“有时先改句子组织比换掉术语更有价值”的方向，但材料是法律文本，不能把效果数值搬到中文光学说明。

[ACCESS/E01](https://arxiv.org/abs/1910.02677)把长度、词汇复杂度和句法复杂度分别控制，提醒我们不要把“给专业读者讲清楚”和“给初学者减少概念”混成同一目标。[BLESS/E03](https://aclanthology.org/2023.emnlp-main.821/)说明通用LLM可以在提示条件下执行句子简化，但这是特定年代和任务的结果，不是对当前GPT版本的保证。

[SALSA/E06](https://aclanthology.org/2023.emnlp-main.211/)将成功与失败定位到具体编辑。可以借鉴其思路，询问“删了什么、补了什么、关系变了吗”，而不是只问“整体是否顺口”。本项目不需要因此运行它的评测代码。

## 6. 两个有用但容易误用的技术概念

**依存距离**描述一个词与句法上关联词之间的间隔。示意地，可写为关联词位置差的平均值：

`D = sum(|i - j| for each dependency edge) / number_of_edges`

把插入解释移到下一句，可能让主体和动作更接近。[P07](https://www.pnas.org/doi/10.1073/pnas.1502134112)研究跨语言的依存长度趋势；它不是“所有句子越短越好”的许可证。中文分词方式、解析器错误和技术符号都会影响自动统计，因此不建议当前仓库加入依存距离硬门槛。

**惊异度（surprisal）**常写为 `I(w) = -log2 P(w | context)`。它依赖选定模型及上下文，不是直接测得的脑力消耗。**均匀信息密度（UID）**讨论信息如何分布，不等于让每句话信息尽量少。[P04](https://aclanthology.org/2021.emnlp-main.74/)指出测量方式和作用范围需要区分；[P08](https://aclanthology.org/2023.tacl-1.20/)表明更大的语言模型并不必然更准确地预测人类阅读时间。所以逐词高亮可以是未来辅助研究方向，不能被命名为精确的“认知负担仪”。

另一个术语需要纠正：**object relative clause是宾语关系从句**，例如 `the file that the script reads`，不是一般的“宾语从句”。中文不能通过机械“补that”复制英文处理方案。

## 7. 提示词、工具与模型训练应该分层

| 层次 | 能做的事 | 负担与边界 | 当前建议 |
|---|---|---|---|
| 写作指令 | 指定读者、任务、要保留的信息和可修改范围 | 不需新增程序；会占上下文；效果依具体模型 | 优先完善 |
| 当前Agent的局部修订 | 对照来源澄清歧义 | 无独立验证保证；不得循环润色 | 沿用现有单轮机制 |
| Vale | 对选定作用域给出明确规则诊断 | 只能覆盖配置实际启用的规则 | 保留，不夸大 |
| AutoCorrect | 提供可选中文排版建议 | 不解决句意与推理；防止误改科学符号 | 按需 |
| 其他lint引擎 | 在既有生态中补特定检查 | 新依赖、规则重叠、误报和维护成本 | 不作默认叠加 |
| 专门简化模型 | 生成候选改写 | 部署成本、领域迁移、语义漂移 | 仅研究参考 |
| 偏好优化/微调 | 改变可训练模型的生成偏好 | 需要训练能力；不是闭源API提示词 | 不进入当前路线 |

[UIDPO/P05](https://arxiv.org/html/2610.14578v1)属于最后一层。它报告的是偏好基准和语言分析，并未证明把其目标译成一句提示词就能取得同样效果。本文只借鉴“不要只看长度”的方向。

## 8. 适配GPT与中文技术文稿

对ChatGPT界面，可以将短版规则放入[自定义指令O02](https://help.openai.com/en/articles/8096356-chatgpt-custom-instructions)；仅服务一个技术项目时，用[项目指令O03](https://help.openai.com/en/articles/10169521-projects-in-chatgpt)约束更小范围。它们与仓库中的Skill安装是不同入口，解压本包不会自动修改这些设置。

对支持相关参数的API，`text.verbosity`用于控制默认详略，而提示词负责必需内容和结构；不能把低verbosity当作可读性开关。[OpenAI部署指导O01](https://developers.openai.com/api/docs/guides/deployment-checklist)也将两者区分。此处不固定模型名或提供未经执行的SDK兼容性保证。

对中文，优先澄清修饰关系、指代、条件范围以及并列/递进/因果区别。不要把英文按空格计数的句长阈值或受控词表直接搬过来。[MCTS/E08](https://aclanthology.org/2024.lrec-main.969/)可提供中文简化研究背景，但它是数据与基准，不是通用中文写作规则。

## 9. 应拒绝的捷径

不建议全局禁止被动语态、无生命主语或专业词；不建议删除may/might/could、不显著、误差范围等限定；不建议“所有句子少于固定字数”；不建议所有段落改成列表；不建议通过随机替换同义词来降低“AI味”；不建议把往返翻译当作语义保真的洗稿过程。

这些做法可能改善一个表面指标，却损害责任归属、术语一致、逻辑连续或研究结论。具体反例见[提示词文档](04-prompts.md)。

## 10. 当前能承诺到哪里

本次可交付的是可追溯的建议和可复核的文字约束，不能承诺阅读时间降低某个百分比。判断“真的更好读”最终需要目标读者和任务证据；lint数量、平均句长、模型偏好分数均不能单独替代。[E07](https://aclanthology.org/2025.naacl-long.327/)还提示句子级指标向长文档迁移的风险。

遵守当前项目边界，本报告不附实验框架或评分流水线。后续维护可以按[演进计划](../../plans/2026-10-26-readability-evolution.md)检查文件是否自洽、范围是否清楚、保护项是否仍在；这些是静态交付条件，不冒充读者效果验收。
